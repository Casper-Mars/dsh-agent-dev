# 实现计划

实现计划不是任务清单，是让另一个人能按步骤做出来的最小指令集。

## Iron Law

> 没有验证方式的步骤，不算步骤。

## 什么时候用 / 不用

- 用：接到编码任务后、改动跨多个文件、需要 TDD、需要并行分工。
- 不用：需求拆解、技术方案设计、验收报告。

## 流程

1. **对齐输入**：AC、方案、当前代码状态、约束（版本、目录、禁止改动）。
2. **定文件边界**：新建 / 修改哪些文件，各自职责一句话。
3. **定接口**：函数签名、入参出参、错误码；先定接口再写实现。
4. **拆小步**：每步一个动作 + 一个可检查结果。默认：失败测试 → 运行确认失败 → 最小实现 → 运行通过 → 提交。
5. **标风险**：不确定的库行为、并发、迁移、兼容性，标出来并给验证方式。
6. **写计划并执行**：计划与现实不符时改计划并说明，不静默偏离。

## 门禁

| # | 门禁 | 通过线 | 不过怎么办 |
|---|---|---|---|
| 1 | AC 对齐 | 每条 AC 有对应步骤 | 补 |
| 2 | 文件边界 | 每个文件职责一句话 | 重写 |
| 3 | 接口明确 | 签名 / 类型 / 错误码 | 补 |
| 4 | 步骤可验证 | 每步有命令或检查点 | 重写 |
| 5 | 风险有验证 | 每个风险有验证方式 | 补 |
| 6 | 范围受控 | 不包含无关重构 | 删除 |

## 输出契约

```text
目标：<一句话>
AC 映射：AC1 → 步骤 2/3；AC2 → 步骤 4
文件：<路径> — <职责>
接口：<签名>
步骤：
1. <动作> → 验证：<命令 / 预期>
2. ...
风险：<风险> → 验证方式
不做什么：<边界>
```

## 反合理化

| 借口 | 现实 |
|---|---|
| 边写边想 | 边写边想会把返工留给测试 |
| 计划太细浪费时间 | 细到可验证，不是细到代码 |
| 先写实现再补测试 | 测试会变成实现的复述 |
| 这个文件顺手改一下 | 顺手改是范围失控的起点 |
| 接口以后再定 | 接口不定，前后端都在猜 |

## 红旗

- 步骤没有验证方式。
- 计划里出现「重构一下」「顺便优化」。
- 先写实现后补测试。
- 接口靠口头约定。
- 执行偏离计划但不更新计划。

## 交接

- 需求不清：回 Leader。
- 方案不清：回 `architect-tech-spec`。
- 执行：Developer；验收：Tester。
