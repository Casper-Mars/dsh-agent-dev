# 代码评审

评审的目标是让变更可维护、可回滚、可验证，不是证明谁更聪明。

## Iron Law

> 没看 diff、没跑测试，不写评审结论。

## 什么时候用 / 不用

- 用：提交前自审、PR 评审、核心逻辑变更、跨模块改动。
- 不用：需求验收、架构选型、格式与 lint。

## 流程

1. **读目的**：关联 issue / AC，确认改动范围。
2. **看 diff**：只改该改的；有无调试代码、临时文件、无关格式。
3. **查逻辑**：主路径、边界、错误处理、并发、幂等。
4. **查测试**：新增行为有测试；失败路径覆盖；测试没被削弱。
5. **查安全**：输入校验、权限、密钥、日志脱敏。
6. **给结论**：approve / comment / request changes；问题分 blocker / major / minor。
7. **写意见**：文件 + 行 + 问题 + 建议，一条一个点。

## 门禁

| # | 门禁 | 通过线 | 不过怎么办 |
|---|---|---|---|
| 1 | 范围清楚 | 关联 AC，无越界 | request changes |
| 2 | 逻辑完整 | 主路径 + 边界 + 错误 | 补 |
| 3 | 测试可信 | 新行为与失败路径覆盖 | 补测 |
| 4 | 无调试残留 | 无 print / TODO / 临时文件 | 清理 |
| 5 | 安全 | 四类检查通过 | 阻断 |
| 6 | 意见可定位 | 文件 + 行 + 证据 | 重写 |

## 输出契约

```text
结论：approve / comment / request changes
范围：<文件数 / 模块>
问题：
- [blocker] <文件:行> <问题> → <建议>
- [major] ...
- [minor] ...
已检查：逻辑 / 边界 / 错误 / 测试 / 安全 / 性能
残余风险：<...>
```

## 反合理化

| 借口 | 现实 |
|---|---|
| 能跑就行 | 能跑不等于可维护 |
| 测试过了 | 测试覆盖不等于边界正确 |
| 这是小事 | 小事累积成维护成本 |
| 作者自己会看 | 评审就是最后一道门 |
| 先合再改 | 合并后的修复成本更高 |

## 红旗

- 只写 LGTM。
- 评审意见没有文件与行。
- 把架构问题当风格问题。
- 要求改与本次无关的代码。
- 没跑测试就 approve。

## 交接

- 方案问题：Leader / CTO。
- 安全风险：CTO。
- 修复：Developer。
