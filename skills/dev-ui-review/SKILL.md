# UI 一致性审查

审查对象是「实现 vs 设计契约」，不是审美偏好。结论必须能指到文件行或截图。

## 输入

- `design_ref`（设计 commit）
- `design/screens/*.md`（屏规格与状态矩阵）
- `design/refs/*.png`（三视口 × 状态）
- 实现代码与运行环境

缺 `design_ref` 直接判不通过，不再往下审。

## 步骤

1. **核对清单**：逐条过 `references/checklist.md`，每条给「通过 / 偏差 / 不适用」。
2. **逐屏逐状态**：每个屏幕按状态矩阵走一遍，缺状态即 blocker。
3. **token 审计**：实现里不得出现 hex / px 字面量；颜色只能来自 `--color-*`，间距来自 `--space-*`。
4. **对比度**：正文 APCA Lc ≥ 60；实心按钮上的文字单独验证。
5. **响应式**：三个断点都看，不只看桌面。
6. **输出报告**：按 `assets/review-report.md` 出结论与偏差表，写清位置与修复建议。

## 分级

| 级别 | 判据 | 后果 |
|---|---|---|
| blocker | 缺状态、缺屏、token 违规、对比度不达标 | 不通过 |
| major | 间距/字号与规格明显不符、断点布局塌陷 | 修完复审 |
| minor | 对齐差 1 档、文案措辞 | 可带条件通过 |

## 禁止

- 凭印象说「差不多了」；必须有对照依据。
- 只看桌面截图，不验证平板与移动断点。
- 替 dev 直接改代码：审查只出报告，修复由 dev 执行。
- 把新需求混进审查结论；发现新需求单独提给 Leader。

## 反合理化

| 借口 | 现实 |
|---|---|
| 状态没做是时间不够 | 状态矩阵是验收标准，不是可选项 |
| 这个颜色差不多 | 差一档就是 token 未使用，按 blocker 算 |
| 移动端以后再适配 | 规格里写了断点，就要在验收范围内 |
| 设计稿没画这个状态 | 回 design 卡补，不要在实现里自行发明 |
