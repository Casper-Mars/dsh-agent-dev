# UI 一致性审查（抽样取证）

审查对象是「实现 vs 设计契约」，不是审美偏好。结论必须能指到文件行或截图。

**复核深度按风险抽样，不按设计资产规模平移。** `design/refs` 有多少张是设计侧的事，
不等于每张 dev 卡都要逐屏逐态比对一遍。

## 输入

- `design_ref`（设计 commit）
- `design/screens/*.md`（屏规格与状态矩阵 —— **以项目自己的为准**，不预设数量）
- `design/refs/*.png`（数量由项目自定，可能是 20 张、240 张，也可能 0 张）
- 实现代码与运行环境

判定规则：

- 缺 `design_ref` → **直接判不通过**，不再往下审。
- 状态矩阵缺失或已过期 → 属**设计侧问题**：记录并升级给 Leader，不算本卡 blocker。

## 步骤

### 1. 定抽样点（默认 3 个）

| 抽样点 | 选法 |
|---|---|
| 主路径 1 | 本卡声称交付的那条交互或那屏 |
| 极端态 1 | `empty` / `error` / `long-list` 任选，挑最容易塌的 |
| 移动断点 1 | 390 宽 |

响应式专项卡才扩到三档（desktop / tablet / mobile）；一般卡不做全量矩阵。

### 2. 取证

按 `dev-ui-verify` 的 L0/L1 流程执行：`browser_viewport` 切视口 → `browser_navigate` +
`browser_screenshot` → `read_image` 看图。**不要为了取证重建截图器。**

### 3. 过清单

`references/checklist.md` 分两段：

- **A 段（blocker 级）**：全量查，逐条给「通过 / 偏差 / 不适用」；
- **B 段（抽样项）**：只在抽样点上查。

### 4. token 审计

实现里不得出现 hex / px 字面量；颜色只能来自 `--color-*`，间距来自 `--space-*`。

### 5. 对比度

正文 APCA Lc ≥ 60；实心按钮上的文字单独验证。

### 6. 是否扩大

- 抽样点出现 blocker，或 ≥2 个 major → 扩大一档（再抽 3 点）；
- 否则收口，不要为了"更稳"把矩阵跑一遍。

### 7. 输出报告

按 `assets/review-report.md` 出结论与偏差表，写清位置与修复建议。

## 分级

| 级别 | 判据 | 后果 |
|---|---|---|
| blocker | 缺屏、缺状态（矩阵里有的）、token 违规、对比度不达标 | 不通过 |
| major | 间距/字号与规格明显不符、断点布局塌陷 | 修完复审 |
| minor | 对齐差 1 档、文案措辞 | 可带条件通过 |

## 什么时候才做全量

只在这两种情况下做逐屏逐态比对：

1. **交付前一次性门禁**（上线前整体过一遍）；
2. 设计侧明确要求全量比对，且写明理由与谁承担时间成本。

其余情况一律抽样。

## 禁止

- 凭印象说「差不多了」；必须有对照依据。
- 只看桌面截图，不验证移动断点（至少一个）。
- 替 dev 直接改代码：审查只出报告，修复由 dev 执行。
- 把新需求混进审查结论；发现新需求单独提给 Leader。
- 要求「逐屏逐状态 × 三视口全量对照」——那是把设计资产规模变成 dev 卡的验证成本。
- 为凑证据重建截图脚本（用 `dev-ui-verify` 的工具链）。

## 反合理化

| 借口 | 现实 |
|---|---|
| 状态没做是时间不够 | 矩阵里写了的状态是验收标准，不是可选项 |
| 这个颜色差不多 | 差一档就是 token 未使用，按 blocker 算 |
| 移动端以后再适配 | 规格里写了断点，就要在验收范围内 |
| 设计稿没画这个状态 | 回 design 卡补，不要在实现里自行发明 |
| 设计稿有 240 张，得全看完 | 资产数量不是验收标准；按风险抽 3 点，出问题再扩 |
