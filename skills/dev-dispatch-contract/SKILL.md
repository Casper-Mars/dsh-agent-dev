# 派发契约

本 Skill 随 `dsh-agent-dev` 发布，只读。

## 触发条件

- 准备调用 `subagent` 工具派发 Developer 或 Tester 之前（组卡片、选 preset）；
- 收到子 agent 完成通知 / 失败回报，需要核对是否符合回报格式；
- 任务需要拆分、改派、打回重修时；
- 用户临时插入新需求，需要判断能否塞进当前派发时（结论：不能，另开一条）。

## 步骤

### 1. 选 preset

| 任务类型 | `agent_preset` | 说明 |
|----------|----------------|------|
| 编码、改文件、写测试、改配置 | `dev-developer` | 所有写操作都走这里 |
| 独立验证、验收重跑、对抗性测试 | `dev-tester` | 编码任务交付前必过一次 |
| 文档 / 脚本类仓库改动 | `dev-developer` | 与代码同等要求 |
| 需求拆解、进度汇报、Wiki 维护 | 不派发 | Leader 元操作，自己做 |
| 任务分支 / worktree 创建、`git commit` / `push` 任务分支、开任务 PR | 不单独派发 | 属 Developer 交付动作，写进卡片（实测：Leader 代做占 15 次调用易出错） |

- `subagent` 的 `agent_preset` 枚举只有 `dev-developer` / `dev-tester` 两项，`dev-leader` 不可作为派发目标。
- `maxDepth: 1`：子 agent 无法再向下派发。需要多人协作时，由 Leader 串行拆成多次派发，禁止让子 agent「自己找人」。
- 一次派发只装一个可独立验收的任务；两个不相关任务塞一张卡片 = 返工。

### 2. 填 12 字段卡片（直接复制改写，**不落盘**）

项目级固定内容（分支 / 基线 / 约定）压到 3–5 行；不抄项目背景、不抄历史评审全文。卡片每一轮都会被重放，抄得越全越贵。

- **卡片直接作为 `subagent` 的 `prompt`，不先 `write` 成文件**：同一段文本写两遍（一遍落文件、一遍进 prompt）纯属浪费，还会在后续每一步重复重放。
- 只有两种场景才写文件：同卡返工要引用上一版、会话中断后需要恢复。
- 卡片自包含：**不引用平台工具名**（不得要求子 agent「去调 `echuan_task_get` 拿正文」）——角色包不依赖平台适配层，平台换了/挂了都不该影响开工。

> 落笔前先过一句自检：**我这条要求，会不会逼他先造一个测量装置？**
> 会 → 改成「要看到什么」，不要写「怎么证明」。

```markdown
📋 任务上下文

1. 任务编号与名称：任务-03 / Skill 内容补全
2. 领域 / 技术栈：node-ts（Node 22 + TypeScript 5 + pnpm 11）
3. 背景 / 溯源（≤1 行）：只写卡片外必需的那一条（如「方案见 docs/tech/x-v0.2.md §4」「上一轮结论见 PR #143」）。
   **不要复述任务目标、范围、依赖、不做清单**——派单消息与平台任务正文里已有，抄进卡片只增重放成本；
   判定依据（AC）不在此项，见第 6 项。
4. 目标（一句话交付物）：把 3 个 SKILL.md 从骨架补成可执行的规则（触发条件 + 流程/细则，按类型补禁止项与检查清单）
5. 路径与分支（项目分支沿用；任务分支与 worktree 由 Developer 自建）：
   - 项目根：<workspace>/projects/<repo>（绝对路径；<workspace> = `pwd -P`，不是 `DSH_HOME`；
     既有本地仓库按它实际路径写，并注明「原地使用，不迁移、不复制」）
   - worktree：<workspace>/projects/.worktrees/<repo>-<任务号>（**本卡自建**，已存在则复用；路径固定，不允许改名）
   - 分支：`task/<任务号>`（从 `origin/feature/<项目号>` 最新提交切出）；项目分支 `feature/<项目号>` 只读引用
   - 本任务基线：`origin/feature/<项目号>` 的最新 commit（写死 hash，不写「最新」）
   - 交付前同步：`git merge origin/feature/<项目号>`；冲突在本任务分支内解决
6. 行为清单（可观察，UI 任务默认）：
   - [ ] `<路由 / 入口>`：`<操作>` → `<看到的可观察结果>`
   - [ ] `<路由 / 入口>`：`<操作>` → `<看到的可观察结果>`
   （逻辑 / 数据 / 接口类任务写成可判定条目：`<命令>` + 预期退出码；两种形态二选一，不要混用）
7. 约束：只写本卡特有约束与授权边界（可改哪些文件、可 push task 分支 / 可开任务 PR）；
   通用红线不抄（「不提交 dist/」「不 git add .」这类见 `dev-role-*`）；禁止改 src/ tests/；frontmatter 只允许单行 key: value
8. 相关关键词与 Skill（必填门禁）：
   - 子 agent 开工第一件事：`skill` 加载 <角色 Skill 清单>，然后 `read references/<stack>.md`
     并回报 `STACK=… REF=… DETECT=…`
   - 派 Developer：`dev-role-developer` + `dev-test-strategy`
   - 派 Tester：`dev-role-tester` + `dev-test-strategy`
   - 关键词：Wiki 检索「Skill 写作规范 / 派发契约」
9. 交付格式：项目分支 + 本任务 commit hash + **任务 PR 链接（base=项目分支）** + diff 范围 <基线>..<commit>；
   证据按 §2.1 分级由 Developer 选（默认 L0/L1；要求 L2 时在本项写理由）；未覆盖项与风险
10. 交付形态与环境（≤2 行）：`delivery_mode: commit|workspace`；容器名；其余按 `dev-environment` 执行
    （不得自行 `docker run` / `devcontainer up`；自建私有环境按该 skill §8 记账并登记 `name=… id=… 已回收|待回收`）
11. UI 设计引用（UI 任务必填）：`design_ref=<commit sha>`；非 UI 任务写「无」。
    必须能对应到 `design/screens/*.md` 与 `design/refs/` 下的截图。
12. 必须覆盖的状态（UI 任务必填）：按屏列出，如 `<screen>: default / empty / loading / error`；
    列表页加 `long-list`；非 UI 任务写「无」。
```

字段硬要求：

- 第 6 项：UI 任务写「路由 + 操作 → 看到什么」，一次观察即可确认；非 UI 任务写「命令 + 预期退出码」。
  两种形态都禁止「体验良好」「符合规范」这类不可观察表述，也禁止要求「每条 AC 一条证明脚本」。
- 第 3 项必须压到 1 行：任务目标 / 范围 / 依赖 / 不做清单**不得抄进卡片**（它们在派单消息与平台任务正文里）。
- 卡片硬上限：≤ 25 行；普通卡 ≤ 1600 字符，带 UI 项的卡（第 11/12 项非「无」）≤ 2000 字符（按字符数，中文算 1）。
  超限的处置顺序：先删第 3 项的复述 → 再压第 10 项 → 最后才动第 6 项（AC 最后一个动，动了就不是同一张卡了）。
- 卡片里不得出现「背景」「范围」「不做」三段的整段摘录；也不得要求子 agent 调工具去取任务正文（不做跨层引用）。
- 第 7 项只写本卡特有约束：可改哪些文件、授权边界（可 push task 分支 / 可开任务 PR）；
  「不提交 dist/」「不 git add .」「不 push --force」这类通用红线不抄，由 `dev-role-*` 约束。
- 第 8 项是**派发门禁**，不是备注：必须写出角色 Skill 清单与路由回报要求，原样成句：
  「子 agent 开工第一件事：`skill` 加载 <清单>，然后 `read references/<stack>.md` 并回报
  `STACK=… REF=… DETECT=…`」。
- 第 8 项写「无」「无 Skill」或留空 = **卡片不合格，禁止派发**（角色规范只有在被加载后才生效，
  不写进卡片就等于没有约束）。
- UI 任务缺第 11 / 12 项（`design_ref`、状态清单）= 卡片不合格，禁止派发；验收按 `dev-ui-review` 执行。
- 第 10 项必须显式写 `delivery_mode`；`workspace` 时还要写清「Tester 如何取得交付物」（复制路径/忽略目录）。
- 路径写绝对路径；相对路径在子 agent 的 cwd 里可能解析不到。
- 第 5 项必须区分「项目级」与「任务级」：项目分支是立项时建的，**任务分支与 worktree 是本卡由 Developer 自建的**；
  路径、分支名、基线 hash 三样必须写死，否则不同卡会撞在同一目录。
  卡片里出现「合并到 main」「自行决定分支名」= 卡片不合格。
- 项目落位硬规则（第 5 项）：新项目 / 克隆项目一律落 `<workspace>/projects/<repo>`，`<workspace>` 用 `pwd -P` 取；
  禁止直接落在 workspace 根、`<workspace>/projects` 根、`$HOME`、`~/project`、`~/agents`。
  卡片给的外部路径要改写成 `projects/` 下并说明；用户坚持原路径才停下确认。既有本地仓库原地使用，不迁移、不复制。

### 2.1 验收形态与证据分级

| 级别 | 用在什么任务 | 交付证据 |
|------|--------------|----------|
| L0 看一眼 | 布局、视觉、文案、断点形态 | 1–3 张截图（写路径）+ 一句结论 |
| L1 走一遍 | 交互、路由、状态切换 | 复现步骤 + 截图或观察记录 |
| L2 断言 | 逻辑分支、数据边界、长期回归 | 脚本 / 单测（只写一次进 `tests/`）+ 退出码 |

- **选择顺序**：能用低档不用高档；UI 任务默认 L0/L1。
- **L2 要理由**：卡片要求 L2 时，必须写清是「回归保护 / 逻辑边界 / 数据边界」中的哪一类；没写理由的 L2 要求视同卡片不合格。
- **证据形态由 Developer 选**：卡片只规定「要做到什么」，不规定「用什么手段证明」。
- **只写一次**：确需长期回归时，断言进项目 `tests/`（或仓库既有测试入口）一次，不许每张卡新建脚本。

### 2.2 切卡规则

- 一卡一屏，或一卡一态组；禁止把「多屏 × 多态 × 三视口」塞进同一张卡。
- 三视口（desktop / tablet / mobile）只在「响应式专项卡」里做；其它卡默认桌面单视口。
- 一张卡最多 6 条行为项；超过即拆卡。
- 拆分按「可独立验收」切，不按「能一次写完」切。

### 3. 调用方式：一卡一会话

不同任务需要的上下文不同。跨卡复用同一个 child，会把上一张卡的全部历史重新算进新卡的每一步输入——实测这类复用会话 84% 的 token 花在旧任务上下文上，上下文一路涨到 50 万 token。所以：

- **新卡** → `subagent({...})` 新建对应角色的 child（`dev-developer` / `dev-tester`），并把 `agent_id` 记进**该卡**的笔记。
- **同一张卡的返工 / 追问** → `send_message(agent_id, message=<新卡片全文>)` 复用这张卡自己的 child；child 结束 ≠ 不可用，同一通道能唤醒。
- **禁止跨卡复用**：上一张卡的 child 不再接收新卡，哪怕角色相同。
- 没记 id 又要给同卡 child 补消息时，才用 `list_agents`（`scope: children`）找回；找回后先核对它是不是这张卡的 child。
- 同一张卡同一时间只允许一个同角色 child；新卡必须新建，不要把新卡塞给旧 child。
- 复用不等于省掉交接：消息里仍要带完整卡片（子 agent 只看得到自己的上下文，拿不到你的历史）。

```text
subagent({
  description: "任务-03 Skill 内容补全",   // 3~5 个词，用于列表展示
  prompt: "<上面 12 字段卡片全文>",   // 卡片不落盘，正文直接进 prompt
  agent_preset: "dev-developer",
  cwd: "/abs/path/to/worktree"
})
```

- `description` 必填，3~5 个词；`prompt` 必填，装整张卡片；`cwd` 指向 worktree，避免子 agent 在错误目录操作。
- 工具会立刻返回 `subagentId`，完成时由运行时推送通知，没有「同步等待」模式。

### 4. 派发后立刻结束本轮

- 派发即结束回合，不写 `sleep`、不轮询 `process poll`、不反复 `git status` 看有没有产物、不发消息追问进度。
- 等待期间**不要**改同一批文件（会与子 agent 冲突），也不要提前开始下一个任务的编码。
- 允许做的事：与本次派发无关的文档 / 记忆维护；或者什么都不做，直接结束回合。
- 完成通知会自动回到本会话，届时再进入第 5 步。

### 5. 收到回报后核对

1. 对照卡片里的 AC 逐条读证据，不读结论句。
2. `git -C <worktree> status --short` 与 `git diff --stat`：改的文件是否在允许范围内。
3. 命令与退出码是否齐全、是否可复现（必要时自己重跑一条只读命令）。
4. 有越界改动 / 缺证据 / 结论与退出码矛盾 → 打回，不进入 Tester。
5. 通过则按 `dev-quality-gate` 走 triage → Tester。

### 6. 完成回报格式（子 agent 按此回，≤15 行）

```text
✅ 任务-03 完成

结论：PASS / 完成待验收
改动：<文件或模块一句话>（<n> 文件 / +a −b）
关键数值：<3–5 个可复核数字>
命令：<主命令> → exit 0
交付：commit <hash> / PR <link>（base=feature/<project>）
未覆盖 / 风险：<一句话>
详情：<PR 描述或仓库内文件路径>
```

- 回执就是平台报告：`echuan_task_report` 的 `summary_md` 用同样内容，不额外扩写。
- 日志、diff 全文、截图清单、逐条断言输出**不进回执**：写进 PR 描述或仓库内文件，回执只给路径。
- 超 15 行视为未按格式回报，Leader 可以只按关键数值 triage 并要求压缩。

## 禁止项

- 禁止只给一句「按需求实现」就派发；卡片缺字段等于让子 agent 猜。
- 禁止不传 `agent_preset`（会落到默认 preset，角色与任务不匹配）。
- 禁止不传 `cwd` 让子 agent 继承 Leader 目录后在主工作区改动。
- 禁止把多个不相关任务塞进同一次派发。
- 禁止派发后 `sleep` / 轮询 / 反复查状态；也禁止中途改同一批文件。
- 禁止跨卡复用同角色 child：新卡必须新建；只有同一张卡的返工 / 追问才 `send_message`。
- 禁止并行起两个同角色 child（同一时间同一角色只跑一个任务）。
- 禁止让子 agent 自行决定验收标准、自行放宽断言、自行 push 项目分支/默认分支、自行合并 PR。
- 禁止在子 agent 回报「完成」后不做 triage 就转交 Tester 或直接交付。
- 禁止卡片第 8 项写「无 Skill」/留空；编码与测试类任务必须写角色 Skill 清单 + 路由声明要求。
- 禁止要求「每条 AC 一条脚本 / 一个断言」——那是在逼子 agent 先造测量装置。
- 禁止在卡片里点名验证手段（指定某个截图脚本、要求把断言/截图脚本写进仓库）。
- 禁止在工具参数里内联长脚本（heredoc / `node -e` / 多行 JSON > 20 行）；先 `write` 落文件再执行。
- 禁止完成回报贴日志 / diff 全文 / 截图清单；只给关键数值与链接。
- 禁止要求超出决策规模的成表证据（一张卡几十条量化指标、整屏截图墙、断言计数）；确需 L2 必须写理由（见 §2.1）。
- 禁止把 Tester 报告当结论而不看证据（报告也可能错）。

### Developer 边界（写进卡片第 7 项「约束」）

- 不拆解需求：卡片给什么做什么，范围外发现的问题写进「未覆盖项」，不顺手改。
- 不调度：不派发其他 agent，需要协作时回报 Leader。
- 不改验收标准：AC 有异议先回报，不自行下调。
- 不 push 项目分支 / 默认分支、不合并 PR、不改他人 worktree；只 push 自己的 `task/<任务号>`。
- 不夹带：格式化全仓库、升级依赖、重命名无关文件一律禁止。

### Tester 边界（写进测试卡片）

- 不改业务代码：发现问题只出报告，不提交修复。
- 不放宽断言：测试必须按 AC 写，不能为了绿灯改预期值。
- 不复用被测方的验证脚本作为唯一证据：至少另写一条独立断言。
- 不替 Developer 修 bug，不替 Leader 做交付决定。
- 不隐瞒失败：跑挂了就写 FAIL + 原始输出。

### 失败回报格式（子 agent 必须按此回）

```text
❌ 任务-03 未完成

1. 卡在哪一步：第 4 步「跑 pnpm test」，tests/domain.spec.ts:42 断言失败
2. 已尝试：重跑 2 次（均 exit 1）；清理 node_modules 重装后仍失败
3. 证据：
   $ pnpm test
   exit 1
   FAIL tests/domain.spec.ts > Skill dev-environment > frontmatter.name 与目录名一致
4. 需要 Leader 决策：A) 放宽断言（不推荐） B) 改 SKILL.md 的 name 字段 C) 先修测试
5. 建议下一步：选 B，我改 frontmatter 后重跑；预计 10 分钟
```

- 五段缺一不可：卡点、已尝试、证据、待决策项、建议下一步。
- 待决策项最多 3 个，每个带选项与推荐，不让 Leader 做开放式问答。
- 禁止只回「失败了」「环境有问题」「需要更多时间」；这类回报视为无效，直接打回重报。

### Leader 收到失败后的处理

| 症状 | 处理 |
|------|------|
| 卡片缺信息 | 补齐字段，原 preset 重新派发 |
| 环境缺失（依赖 / 中间件） | 派 `dev-developer` 装依赖或起中间件，再重派原任务 |
| 代码错误 / AC 不达标 | 附失败证据打回 `dev-developer`，不自己修 |
| Tester FAIL | 回 Developer 修，修后完整重跑 typecheck/test/build |
| 超时 / 无产出 | 查 `git status` / `git diff`：有产物走 triage，无产物缩范围重派 |
| 越界改动 | 打回并要求回退越界部分，保留有效改动 |

## 检查清单

### 派发前
